# 进度条与运行日志稳定化清单

状态：P0 已在源码完成并通过回归；尚未打包或发布。

## 目标

用户看到的进度条必须来自任务的真实结构化状态；用户日志必须简洁、可理解、可定位。诊断原文必须保留，但不能再依赖日志关键词来驱动任务进度或判断任务结果。

本清单不改变 AI 选片、字幕、裁切、动态缩放或语音识别业务逻辑。

## 当前链路

### 任务与进度

1. `web_client/server.py` 用内存 `_TASKS` 保存任务的 `status`、`progress`、`message`、`error` 和部分批量统计。
2. 工作流在关键节点调用 `_set_task_progress()`；批量工作流额外从消息文本解析 `处理 N/M`、`跳过失败 N/M` 等统计。
3. `_task_log_fn()` 会从普通日志文字匹配关键字，推断阶段和百分比。
4. 前端轮询 `/api/tasks`，并通过 `/ws/log` 接收日志；`web_client/frontend/assets/app.js` 又维护一套相同的关键词推断规则。

已有能力：数值进度不会倒退；批量任务能记录成功、失败和内容不足；单个素材失败后批量任务能继续。

主要问题：

- 后端和前端重复维护阶段关键字，日志文案变化会让两端显示不一致。
- 固定百分比只表示粗略阶段。长视频的 ASR、转码、切割和画面处理耗时不同，用户无法判断是在工作还是停滞。
- 总任务进度与“当前第 N/M 个素材”的内部进度没有标准字段，只能从文字中猜。
- `progress`、`message`、`error` 混在同一个任务对象，无法表达“任务仍在继续，但当前素材失败”“任务成功，但存在可恢复警告”等状态。

### 运行日志

1. `emit_log()` 将日志写入内存队列 `_LOGS`，最多保留 1500 条；WebSocket 新连接只回放最近 80 条。
2. `_simplify_log()` 会压缩、清洗、去重或隐藏低层输出，再把结果显示到页面日志区。
3. 每个 scope 只保留最近一条相同日志的去重键；日志事件没有稳定的 `task_id` 关联字段。
4. 高级诊断能够看到部分原文，但页面刷新、服务重启和同一 scope 的后续任务会削弱定位证据。

主要问题：

- 用户可读日志、机器进度信号和底层诊断混在同一条文字链路。
- 同一个 `smart-cut` 或 `mix` scope 的历史任务可能混在一起，无法可靠地按任务回放。
- 重要错误有时被压缩得过短，普通提示又可能被大量阶段日志淹没。
- 内存日志有上限，长批量任务或页面刷新后，问题现场可能不完整。

## 目标模型

### 结构化任务状态

每个任务只由后端更新下列字段；前端只负责渲染，不再从普通日志推断进度：

```json
{
  "id": "smart-cut-...",
  "scope": "smart-cut",
  "status": "running",
  "phase": "cut",
  "phase_label": "裁剪片段",
  "overall_percent": 72,
  "item_progress": 64,
  "item_current": 2,
  "item_total": 8,
  "phase_current": 7,
  "phase_total": 19,
  "message": "正在处理第 2/8 个素材",
  "warnings": [],
  "error": ""
}
```

阶段枚举固定为：`prepare`、`normalize`、`asr`、`ai_select`、`visual`、`cut`、`assemble`、`dedup`、`subtitle`、`verify`。

规则：

- `overall_percent` 只能前进，完成、失败和取消统一为 100%。
- 可计数操作必须提供 `phase_current/phase_total`，例如切割 `7/19`；不可计数操作只显示阶段与已耗时，不虚构剩余时间。
- 批量任务必须同时提供素材层的 `item_current/item_total` 和任务层的 `overall_percent`。
- 圆形进度条只渲染 `overall_percent`；横向进度条只渲染当前素材的 `item_progress`。单素材任务两者数值相同。
- 单素材失败进入 `warnings` 与批量统计；只有任务整体无法继续时才设置 `status=failed`。

### 分层日志事件

每条日志必须绑定 `task_id`，并拆分为显示信息和诊断信息：

```json
{
  "event_id": 123,
  "task_id": "smart-cut-...",
  "scope": "smart-cut",
  "time": "10:28:34",
  "level": "warning",
  "kind": "fallback",
  "display_message": "硬件加速不可用，已改用稳定编码。",
  "diagnostic_message": "...原始 FFmpeg 信息...",
  "phase": "assemble"
}
```

日志类型限定为：`stage`、`info`、`warning`、`error`、`fallback`、`result`、`diagnostic`。

规则：

- 页面默认只展示 `stage/info/warning/error/result`；`diagnostic` 只在高级诊断中展开。
- 普通日志应表达发生了什么、是否继续、下一步建议；不展示冗长命令、临时路径或重复帧输出。
- 原始诊断按任务写入用户数据目录的轮转 JSONL 文件，保留有限天数和总容量；不能只存在于内存队列。
- WebSocket 按 `task_id` 续传，不再只按 scope 和最近 80 条推送。
- 页面刷新后通过 `/api/tasks/<task_id>` 与 `/api/tasks/<task_id>/logs` 恢复同一任务的进度、警告和诊断摘要。

## 页面展示

任务面板保留一个总进度条，但显示两层信息：

```
总进度 46%   当前：第 2/8 个素材
裁剪片段     7/19
```

日志区域分为：

- **运行摘要**：当前阶段、最近成片、失败原因、可恢复警告和批量统计。
- **运行日志**：按时间显示用户能理解的任务事件，默认只显示当前任务。
- **高级诊断**：按任务查看可复制的原始错误、FFmpeg/ASR/AI 细节；不影响普通用户阅读。

失败时，进度卡必须显示：失败范围（当前素材或整个任务）、简短原因、是否已继续、建议操作。不得只显示“100%”或一条没有上下文的 FFmpeg 返回码。

## 实现优先级

### P0：任务与日志绑定（已完成）

1. 给 `emit_log()`、任务日志回调和 WebSocket 事件增加 `task_id`。
2. 任务记录增加 `phase`、素材层进度、警告列表和最终结果摘要。
3. 让智能成片、混剪、AI 预览、单品扫描和批量任务都从同一任务状态辅助函数更新。

本次实现：所有 Web 任务线程自动带入 `task_id` 日志上下文；任务状态新增阶段、总进度、当前素材进度、当前素材、子步骤、警告和最后事件时间；批量任务已有的失败明细在异常区逐项显示，并在新的输出历史中保留安全摘要；新增按 `task_id` 查询当前内存日志的接口。

### P1：进度条只消费任务状态

1. 前端优先读取结构化任务字段。
2. 移除后端 `_task_log_fn()` 与前端 `progressStageRules` 的重复关键词进度推断。
3. 旧日志解析仅保留为历史任务兼容，不得驱动新任务状态。

### P2：日志分层与持久化

1. 将显示日志与诊断原文分开，错误保留完整原因和关联任务。
2. 增加按任务查询和页面刷新恢复。
3. 增加有边界的本地日志轮转与“清理日志”行为核验。

### P3：长任务体验

1. 展示当前素材、片段计数、已耗时和可恢复失败数量。
2. 仅对可量化的 FFmpeg/切割/下载阶段给出子进度；AI 与 ASR 不显示虚假的预计剩余时间。
3. 对卡住的任务显示“最后事件时间”和“正在等待的阶段”，方便判断是否需要停止或诊断。

## 验收矩阵

| 场景 | 必须结果 |
| --- | --- |
| 单个智能成片 | 阶段、数值、日志与最终状态一致 |
| 多素材批量 | 同时显示总进度、当前素材和已跳过数量 |
| 长 TS/长视频 | 长时间阶段不伪造完成；显示已耗时和最后事件时间 |
| 单素材失败继续 | 当前素材错误可追溯，任务继续，统计准确 |
| 页面刷新或 WebSocket 重连 | 恢复同一 task_id 的任务摘要和日志，不串入旧任务 |
| FFmpeg/ASR/AI 失败 | 用户日志有短原因和建议；高级诊断可复制完整错误 |
| 清理日志 | 仅删除已过期诊断，不影响运行任务与用户配置 |

## 与 V4 发布的关系

P0 和 P1 应在 V4 首个正式候选前完成或明确排除。它们属于业务包变更，不需要替换 V4 Core；完成 V4 基线后，后续可作为正常签名业务增量发布。
