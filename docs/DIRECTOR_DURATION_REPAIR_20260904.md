# AI 导演时长修复：本地实现与未通过项

日期：2026-09-04。结论：程序反馈闭环已接入，已验证原链路MP4输出；长目标稳定性尚未通过验收，未发布、未推送。

## 已确认的原问题

原始 `mix-1788474438-5cda6a` 请求90秒。AI选中的17条原声合计39.36秒，却在停止理由中自称约72.89秒；所有ID都进入了原计划，不是执行层把90秒删成39秒。

旧链路存在三个可修复缺口：故事未分配章节原声预算；模型算错时长后没有收到程序实测反馈；选片和导出没有统一考虑变速后的最终秒数。

## 本轮变更

- 在原有故事调用里增加章节原声预算和讲清标准；仍先定购买故事，不选具体句子。
- 原有Casting继续从完整安全字幕池选择1–5秒短Beat，允许既有5–8秒完整例外；增加章节展开说明、时长核算、缺少的上下文说明。
- 使用现有导出DurationContract：用户秒数是最终成片秒数。默认容差与导出一致，为±max(5秒,目标/6)。自定义容差照用；原声预算乘导出速度，不把120秒×1.15的138秒预算截为120秒。
- 程序逐ID计算总时长、各章时长、预算差额和预计最终时长。偏离区间、模型明确报告未闭合、无效来源或重复引用时，最多回同一Casting步骤校准一次；不是新增Planner，也不是程序自动补句。
- 常规2次AI；有偏差时最多3次。失败不无限重试，空片单也不能回退进历史多Prompt规划器。不可执行的修订回退到初稿；重复等质量问题保留告警，不由程序删句。冻结故事顺序和实际已选开头，不用不一致的opening记录替换真实开场。
- 预览显示原声/预计成片，未达标不能因AI自称pass而隐藏；故事质量评价与纯时长达标分开。
- 若当前全部安全短句的总时长上限也不足目标，明确显示候选池的物理上限。它不是“这些句子全都有新价值”的承诺，也不替用户放宽内容规则。
- 缓存纳入容差、导出速度及新合同版本；切换备选方向保留速度设置，费用提示为通常2次、最多3次。
- 实测遇到模型返回JSON尾逗号，增加只作用于字符串外的确定性格式修复；不改原话或ID，不恢复截断内容。

没有改M3物化实现、音频尾字保护、逐词编辑、人工调整或剪辑渲染算法。

## 实测：不能只报好看的数字

全部选句来自真实模型返回，没有人工替换。新测试使用1.15倍导出速度，表中为程序算出的预计成片秒数。

该半裙片单随后经过原有智能成片链路，实际带字幕MP4为 **76.277秒**，进入90秒目标的既有75–105秒区间。预计秒数与真实文件秒数分别记录，不混称；没有人工换句或额外导演AI调用，未修改渲染算法。这个样本只证明执行成功和文件时长，不证明口播质量全部达标。

运行中另观察到用户刚完成的 `smart-cut-1788524955-59cbf8`：鹅绒服，60秒目标，23.64秒原声/20.56秒预计成片。该次选片后未用候选仅4条/9.795秒；整个当前安全短句池合计33.435秒，1.15倍速后物理上限29.074秒，低于该次用户设置的45秒下限。不能把此例与“池内有充足内容但AI没选够”混为一谈；它需要检查内容限制/补充素材，而不是单纯重试AI。本轮未修改它的内容规则或重选历史片单。

120秒校准返回的原声也没有达到所需预算。没有为了通过验收放宽容差，也没有补静音、慢放、循环或程序添加内容。

第一轮60秒测试脚本漏传正式链路的`commerce_lite_final_editor=True`，误进入了历史M2路径。因此最初该次case的旧M2状态不能作为正式链路证据。已修正脚本，用保存的真实故事/Casting/校准原文离线重放，未新增AI选句，表中采用修正后的正式执行结果。

第二轮/单商品测试使用正确的正式分支。保存首次模型返回及离线复放记录，不用重复调用来掩盖失败。`--replay`严格禁止缺失缓存时再发AI请求。

## 剩余瓶颈

更明确的秒数要求并未让模型稳定选够内容。仍可看到：章节预算高于真实选择、同义证明重复、部分句子依赖上下文，以及不可执行ID。不能把“程序算得准”和“AI已能把每章讲充分”混为一谈。

当前不是稳定的90/120秒发布修复。不要仅凭测试数量发布，不要把短版改标为素材不足，也不要增加多轮自动语义否决或用程序拼足时长。下一步应针对这些保存的失败片单，验证AI对具体章节缺口的展开能力；保持同故事、同素材和短Beat节奏，按真实口播检查新增价值与闭合。
