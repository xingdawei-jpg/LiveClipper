## 2. 方案二：缩短 AI 返回数据，保留选句与时长能力

### 2.1 第一批实施内容

只改变第二次选片回复的传输结构。仍把完整、有序字幕交给 AI，仍由 AI 决定每句 ID、原有顺序、商品归属与章节；保持低强度推理和现有输出容量。

1. **商品名称和类型集中定义。** 回复顶层新增 `products`，每个不同的“商品名、类型”组合保留独立记录；每条短句用 `product_ref` 显式引用。不自动把“上衣”“裤子”“套装组件”合并，也不因名称近似而认为是同一商品。
2. **缩短高频字段名。** 例如 `subtitle_ids → ids`、`beat_function → role`、`source_seconds → sec`、`product_relation → rel`、`product_evidence_ids → evidence`。保留命名对象，避免改成易错的长位置数组。
3. **关系逐句保留。** 同一个字幕 ID 在不同方案里可能承担不同职责，每次出现都保留其关系、证据、搭配支持说明和套装组件标记；不能只用字幕 ID 建一张全局语义表来替代。
4. **接收后还原现有结构。** 新增有版本号的转换层，在商品审计、时长审计、候选物化之前，把紧凑数据还原成现有字段。工作台、编辑草稿及渲染继续接收原结构。
5. **严格检查引用。** 重复产品编号、找不到的引用、空类型、非法关系、缺失证据都明确报错，不猜默认值。保留旧结构读取能力，方便历史预览与离线重放。

示意结构（仅展示一条短句，其他原有字段继续保留）：

```json
{
  "schema_version": "director-wire-v1",
  "products": [{"name": "格子夹克外套", "type": "outerwear"}],
  "packet": {
    "strategies": [{
      "strategy_id": "S1",
      "chapter_packets": [{
        "chapter_id": "C1",
        "beats": [{
          "ids": [101], "role": "proof", "sec": 2.4,
          "product_ref": 1, "rel": "main_product", "evidence": [99]
        }]
      }]
    }]
  }
}
```

这个第一版不删除章节预算、每句秒数、累计时长、开场比较、商品证据，也不要求模型减少思考。缩写和商品引用关系由模型明确返回，程序只做确定的格式展开。

### 2.2 已完成的免费体积试验

对已付费的三份真实选片回复做了离线编码与反向还原。所有字段值、数组顺序及有无字段保持一致，反向结果与原 JSON 对象完全相等。

| 样本 | 原结构压紧后的字符数 | 引用与缩写后的字符数 | 字符减少 |
|---|---:|---:|---:|
| 智能三方案 | 29,072 | 19,143 | 34.15% |
| 混剪预览三方案 | 37,539 | 23,022 | 38.67% |
| 直接混剪三方案 | 32,860 | 22,800 | 30.61% |

比较双方都已去掉排版空白，避免把缩进变化冒充结构收益。直接混剪样本保留了 8 组不同的商品名称/类型组合，没有把它们归并成 1 个。这是结构可逆和字符体积证明，不是模型能稳定生成新格式、tokens 会等比例下降或时长质量不变的证明。

按上述 90 秒混剪样本举例：如果未来实测选片正文 tokens 真能减少 30%–40%，其他用量完全不变，单次大约节省 ¥0.019–0.025，即总费用约 7%–9%。字符数不能直接换算成 tokens，这只是条件估算。推理耗时可能不变，不能承诺速度同比例改善或降至 ¥0.1 以下。

### 2.3 第二批可选内容

在第一版真实稳定后，再评估第一遍故事回复的共用商品信息、空的非必要说明字段，以及重复输出的长篇审计理由。保留标题、购买欲望、章节职责、商品范围和预算；不把三个方向强行套成同一个商品范围或章节表。不将这批收益提前加进第一版估算。

### 2.4 改动位置与验收

- `app/commercial_analyzer.py`：`build_two_pass_cast_prompt` 的新返回样例；解析后的版本分流及转换调用。
- 建议新增 `app/director_wire_schema.py`：只承担解码与结构检查，隔离出不涉及语义选择的可逆转换。
- `app/director_product_contract.py`、`app/single_pass_director.py`：原审计、展开链仍读取完整字段；针对转换输出补充集成验证，不放松准入规则。
- `run_m3_new_golden_plan_fidelity.py`：分别保留模型原始回复和展开后的数据，明确哪个来自 AI，哪个只是转换结果。
- 提示词协议/相关预览缓存版本随返回结构升级，避免旧缓存错误跨版本命中。

验收先使用已保存回复和故障样本，不付费。覆盖：一/三方案、单品/套装/搭配、不同来源出现相同 ID、缺失引用、矛盾名称类型、空值/未提供值、旧格式以及未知版本。要求展开前后字幕 ID、顺序、章节、秒数和商品审计结果一致。

接着由用户测试新模型回复：智能/混剪，单/三方案，60/90/120 秒；先小范围，再补组合。分别记录输入、缓存、推理、正文、总费用和各阶段耗时。先确认无格式及引用失败、无新增无效 ID，时长及连贯性不退化，再比较至少三次同条件运行的中位数。不同片长或不同方案数不能当作同条件性能对比。

## 3. 方案三：加速源素材准备和多成片最终字幕

### 3.1 已经有的能力与实际缺口

- 源素材旁的 `.srt`、`.words.json`、`.asr-cache.json` 已持久保存；后续预览和直接成片已复用。继续使用当前文件身份、字幕及词级文件校验。
- `app/stt.py` 已有 `LocalASRWorkerSession`，支持同任务多个音频顺序复用同一识别进程和模型，任务结束释放。
- `transcribe_local_audio_to_srt` 已支持 `worker_session`，但 `generate_srt` 与 `server._ensure_srt` 没有透传；`_prepare_mix_director_source` 逐文件调用，因此多个未识别视频会逐个重新启动模型。
- 直接多方案渲染循环没有把该 session 传入 `_run_mix_from_preview`。尽管下层 `run_mix` 和最终字幕函数已支持 session，当前入口没有贯通。

真实日志显示：part_005 的进程启动至识别开始约 80 秒，part_006 约 71 秒；其中“加载模型”日志前分别有 69、60 秒，当前源码在这段执行运行库注册与导入等工作。尚未拆分具体模块、磁盘或其他等待，因此不能断言全部是模型权重加载，更不能承诺单文件冷启动能全部消掉。

三套直接成片的最终字幕也分别等待了约 67–68 秒才进入识别。它们必须识别各自成品音频，但模型可以复用。

### 3.2 优先接通已有任务内复用

**源素材准备：**

1. 在混剪源准备阶段创建惰性 session；只在确有文件需要本地 ASR 时启动进程。缓存全命中时不启动模型。
2. 从 `_prepare_mix_director_source → _ensure_srt → generate_srt → transcribe_local_audio_to_srt` 透传 session 和同一个任务取消信号。
3. 未识别素材顺序提交，同批第二条开始复用已加载模型。源素材准备全部完成后在 `finally` 关闭，避免 AI 请求等待期间占用模型内存。
4. 视频身份、文本及词级文件哈希、ASR 配置变化仍要检查；只按同一实际素材复用，不按文件名猜测。用户提供的字幕和人工编辑不被覆盖。

**三方案最终字幕：**

1. 由直接成片的外层版本循环持有另一份惰性 session，通过 `_run_mix_from_preview` 传至 `run_mix` 和 `_add_subtitles_final`。
2. 每个成品仍独立提取最终音频、识别、CTC 对齐并保存自己的字幕。只复用模型，不复用其他版本的识别文本或时间戳。
3. 同样接到智能多版本和工作台多方案渲染入口，避免仅修混剪直接成片而其他入口仍重复加载。
4. 无字幕输出、云端识别成功等不需要本地模型的情况不启动 worker。最外层拥有关闭权；被传入 session 的内层不提前关闭。取消/超时/崩溃均结束进程并清理未完成的临时结果。
5. 最终字幕模型可能要跨两个版本之间的渲染等待驻留。测量峰值内存；若导致换页或拖慢渲染，应释放并退回独立识别，不能只看 ASR 自身变快。

**预期收益范围：** 多个全新源文件，预计减少后续文件的重复启动；已有字幕的文件不应计入节省。三方案最终字幕按此次日志有约两次、各一分钟左右的启动等待可争取省掉。实际净收益取决于内存、冷暖状态和 worker 复用表现；单个新视频仍需首次启动与完整识别。该项主要省时间，不直接减少 DeepSeek tokens 或费用。

### 3.3 耗时记录先补准确

目前内部预览、每个渲染版本都用同一任务 ID 写 `started_at`，会覆盖最初开始时间。本次直接成片真实日志范围为 15:14:07–15:50:43，约 36 分 36 秒；任务字段最后却只覆盖第三版开始后的时间。后续性能验收不能直接使用这组被覆盖的起止值。

建议顶层首次启动时间只写一次，阶段单独记录：缓存检查、音频提取、进程启动、库注册/导入、模型加载、分段识别、CTC 对齐、字幕写入、词级映射、候选准备、故事 AI、选片 AI、预览还原、每版渲染、每版最终字幕。后台保存详细时间；界面继续只显示清楚的阶段和简短耗时。

同时修正两处会误导诊断的日志：

- 原文“未启用云端语音识别，正在使用本地语音识别”被展示成“正在使用云端语音识别”，原因是日志文本匹配顺序与否定句型覆盖不全。
- 直接复用片单渲染时旧混剪日志仍写“调用 AI 选片”。应根据是否使用既有片单显示对应信息，费用以真实请求记录为准。

### 3.4 测试与后续优化边界

先测试两条短音频的进程复用、不同输出隔离、缓存全命中零启动、取消/崩溃后的进程释放。再用同一组实际源视频比较冷缓存、暖缓存、仅新增一个视频；验证源字幕文本、词级时间和质量报告保持一致，尤其不能丢失 `.words.json`。

最终字幕复用需验证三个成品各自的音频身份、词级边界、手动编辑与最终 FFmpeg 烧录。按任务总耗时以及峰值内存评价，不只统计少启动两个进程。

本轮不把高耗时 ASR 替换成低质量模型，不取消 CTC，不默认改为收费云端服务。第一批也不增加全局常驻模型、多进程同时抢 CPU 或全量候选缓存。只有阶段计时证明确有重复热点，才增加相应缓存；缓存候选时必须纳入素材顺序、SRT/词级内容、词库/规则、协议版本等身份，且不得把旧任务的商品关系或已选结果误复用。

## 4. 本次失败的确切原因与修复方案

### 4.1 15:14 的真实失败

任务：`mix-1788678847-e4d03c`。阶段：第一次故事规划。原始回复第 177 行、第 33 列：`opening_promise` 字符串中嵌入了一对没有转义的英文双引号。

供应商回执 `finish_reason=stop`，输出 5,097 tokens，上限 12,000；所以本次是字符串格式错误，不是输出截断、时长审计失败或模型超时。代码已发送 `response_format=json_object`；不能把原因归为没有启用 JSON 模式。

离线仅给那一对内部引号增加两个反斜杠后，整份原回复可解析为三个方案。没有修改文字、ID、预算或顺序；没有将这份试验修复写回原任务，也没有用它重放业务流程。现有修复仅覆盖 `relation` 行末漏引号等有限情况，不能处理这次 `opening_promise` 内部引号。

直接成片已有一次自动重试机制：15:14:49 开始重试，第二次故事和选片均成功；15:20:00 进入渲染，15:50:43 任务完成，三个 MP4 文件均存在。这里仅确认错误恢复和文件生成，不代表成片质量或全部时长验收通过。日志记录三版真实时长分别为 90.7、67.5、72.4 秒；以 90 秒目标衡量，后两版仍有偏短问题，不能在本方案中把它们标为时长达标基线。

### 4.2 失败费用和报告缺口

| 范围 | 调用数 | tokens | 谷时估算 |
|---|---:|---:|---:|
| 第一次故事回复，业务解析失败 | 1 | 26,803 | ¥0.024129 |
| 成功的重试故事与选片 | 2 | 97,778 | ¥0.228697 |
| 本次直接成片实际 AI 合计 | 3 | 124,581 | ¥0.252826 |

失败报告保存在 `failure.json`，原账本保留三次调用。重试创建新的预览 session，成功后的 `ai_cost_report.json` 按新 session 汇总，因此只显示两次成功调用、97,778 tokens，并且 `retry_count=0`。这是任务汇总与重试关联不完整，不是供应商免收失败费用。

建议：按顶层任务聚合所有 attempt/session 的 request ID，去重后计费；同时保留各次尝试明细。API 返回成功与业务解析成功分别记录。每次尝试独立保存文件，最终任务报告包含失败消耗。用户界面仍只显示一个峰/谷时估算金额，必要时加“含 1 次重试”，不恢复复杂计算面板。

### 4.3 格式故障修复优先级

1. 在人类可读说明字段中约定中文引号或不使用嵌套引号，缩短说明长度；这是预防，不能代替解析检查。
2. 增加严格限定的本地格式恢复：仅在完整回复、明确的说明字段边界及唯一可确定的转义位置上补转义，保留原始回复、修改位置与修复后副本。结构、字幕 ID、秒数、商品关系或缺失容器存在歧义时不恢复。修复后必须严格解析、检查重复键，并通过原来的结构和语义约束。
3. 将现有的一次重试预算按失败阶段执行。故事失败只重试故事；选片失败复用已经成功的故事、原始素材和配置指纹，仅重试选片。正常仍两次 AI；故障重试不是第三次时长后补。总重试预算不增加，不为了凑时长重试。
4. 日志明确“故事回复格式错误，正在重试”，避免用“格式不完整”让用户误以为又被输出上限截断。记录具体失败阶段和错误码，并把耗时、费用合并到同一顶层任务。

### 4.4 15:20 的硬件自检失败

日志还包含另外两条“自检失败”：NVIDIA 编码器未能加载 `nvcuda.dll`，AMD 编码器未能加载 `amfrt64.dll`。它们只是探测的两个编码后端不可用；随后 Intel `h264_qsv` 自检通过并被选中，渲染继续。这两条不是 AI 故障，也没有消耗 DeepSeek tokens。

同一批三版成片重复探测了一遍硬件。可将成功编码器及不可用后端结果在一次顶层渲染任务内复用；实际编码失败时立即使缓存失效并走现有回退。界面正常情况下只显示“已启用 Intel 硬件编码”，失败后端原因放在诊断信息里。无需为这两条探测结果安装不匹配的显卡驱动。

## 5. 建议落地顺序

1. **先修格式恢复、按阶段重试及全任务费用汇总。** 用这份真实失败回复做离线回放，能直接验证是否避免额外请求和漏计。
2. **接通现有 ASR session，并补准确阶段计时。** 覆盖源素材与三套成品的字幕阶段，保留独立进程及任务结束释放。
3. **落地紧凑选片返回结构。** 先完全可逆，再用用户的新预览和直接成片做实测，保持现有时长推理和输出容量。
4. **根据测量再决定第二批。** 包括单次冷启动内部热点、候选构建、预览还原及渲染耗时；不把未定位的几十秒统一归结为缓存问题。
